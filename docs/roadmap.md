# Roadmap

Roughly in order. Each step should leave a torch that's no worse than the step before. Tick things off here in the commit that does them.

## 1. It lights up

- [x] Toolchain with nightly `avr-none`, `rust-lld`, own linker script and vector table, no crates
- [x] Pin map and registers for the TS21 (model 0614) driver
- [x] Switch sampling at 64 Hz and a click/hold decoder
- [x] Two-channel ramp (linear then FET), 150 levels
- [x] Click on, click off, at one level on the linear channel
- [x] A built-in UPDI programmer in `xtask` (ping, backup, flash, restore), tested against a fake chip
- [ ] Ping, back up and flash a real TS21, which is also the first real test of the programmer
- [ ] Confirm the batched UPDI frames work on a real chip. `write_page` now sends the RSD toggle, REPEAT, the page data and the RSD toggle back in one frame, and `read` sends REPEAT and LD together. The fake chip is happy with both; if a real flash fails partway through a page, split them back into separate sends first. Flash is committed with PAGEWRITE (0x01) and EEPROM with PAGEERASEWRITE (0x03), and only the fake chip has seen either, so if flash fails `verify` and EEPROM doesn't, suspect PAGEWRITE.
- [ ] See whether the `wait_nvm` after `NVM_PAGE_BUFFER_CLEAR` ever sees the controller busy. pymcuprog waits there, so keep it unless a real chip shows the first poll is always idle. It's one round trip per page.
- [x] Check PB5 is the button LED and decide what it does: amber, always on, lit by its pull-up
- [ ] See the amber button LED glow on a real TS21, which is the first check that PB5 is it
- [ ] Bring back the full UI from the `fancy-ui` branch, with ramping, moonlight, turbo and lockout

## 2. It's safe to leave a cell in

None of this is optional for a light with a direct-drive FET on a 21700.

- [x] Sleep when off, in power-down. Power-down draws the same as standby with everything stopped, and the PIT still runs in it (DS40002204A §23.8), so standby buys nothing here, and the one loop carries on every tick, on or off. That leaves the watchdog's feeding as it was (the WDT counts in every sleep mode, §19.3.4), and samples PA5 every tick, so PA5 needs no interrupt. PA5 is only partially asynchronous, so a pin-change wake would need a level that lasts until the clock restarts (table 16-3), and a press seen by the PIT tick has no such trouble. `Torch::resting` is true with the light off and no click being counted, and `hw::wait_for_tick` powers down on it. `Limits::rest` stops the ADC work, since it can't run in power-down (§30.3.5), so a press restarts the voltage readings, in time for the click, and a battery ceiling only climbs while the cell's being read. After five minutes of rest (`battery::FORGET_TICKS`) the filter forgets the cell, so the first reading stands alone. Any sooner and clicking off and on would reseed it from the unloaded voltage each time, keeping a nearly flat cell running. Anduril also slows the PIT when off, but that fights the watchdog window (see the watchdog item), and the off pass is only 238 instructions. That's about 50 µs awake with the 10 µs wake-up (table 36-6), so around 10 µA on top of a sleeping chip's 1 or 2 µA. Likely, not measured. The button LED's pull-up dwarfs that at 50 to 64 µA, so the torch comes to about 600 mAh a year, before the rest of the driver. A separate rest loop that skips `Torch::tick` could save most of the 10 µA, but next to the LED that isn't worth a second place feeding the watchdog. A handler still mustn't touch TCA0's 16-bit registers, since they share one TEMP byte with the main loop and an interrupt mid-access corrupts it (§8.5.6), or it has to save and restore TEMP. The simulator lands the handler on the instructions a run reaches, between a TCA0 low and high byte included, and refuses a handler that touches those registers there. It also lands the real tick on each of the instructions before `sleep`, which nothing but a long pass could do now the switch has no interrupt. Interrupts wait out the CCP window (§8.5.7), four instructions after a write to SPL or the next I/O write (§8.5.4), and the instruction after `sei` (DS40002198C), all from the documents and still to check on a real light. Before sleeping, `hw::prepare_sleep`:
  - Turns ADC0 off, and clears `VREF.CTRLB.ADC0REFEN`, which forces the reference on. The datasheet gives no current for either left on in power-down, and Anduril turns the ADC off too. `hw::adc_start` turns both on again when `sensors::Schedule` next sets the ADC up, and the conversion it throws away gives the reference a tick to start.
  - Checks both TCA0 compare registers have reached 0, not only the BUF registers, and stays in idle for a tick if they haven't. The datasheet doesn't say what a waveform output does in sleep, so it clears CMPnEN too, leaving the pins to PORT, whose OUT is 0.
  - Leaves the unused pins as `hw::init` set them, pulled up with their input buffers off (AN2515C §9), all but PA0, which is UPDI.
- [ ] Measure the off current on a real light, against the 60 to 75 µA or so above, chip and button LED together. Whether the BOD's on matters here (see the BOD item), and so does whatever the rest of the driver draws. It's also the check that a `wdr` survives power-down: §19.3.6 has it syncing for 2 to 3 WDT clocks, the loop sleeps straight after feeding, and the datasheet doesn't say the sync finishes with the peripheral clock stopped. If it doesn't, the chip resets over and over while off, which looks like milliamps here and nothing else, since the light stays off and a press idles, so feeds land.
- [x] Sleep between ticks, in idle sleep, with the RTC PIT interrupt in place of the busy-wait. It did this off as well as on, until power-down (above) took over when off. Standby is out: TCA0 has no RUNSTDBY, so standby stops the PWM (§11.3.2.1). `hw::rtc_pit` clears the PIT's flag and sets a bit in `GPIOR0` (AN2515C §4.5 suggests GPIORs for shared flags, since `sbi` and `cbi` reach them in one instruction), and that's all. `hw::wait_for_tick` uses AN2515C §4.5's pattern so it can't sleep through a tick that's already happened: with interrupts off, check and clear the bit, and if it wasn't set, `sei` and `sleep` back to back, since the instruction after `sei` always runs before a pending interrupt. `hw::init` sets `RTC.PITINTCTRL.PI` before `PITEN`. Errata DS80000886C 2.6.1 and 2.6.2: any write to `RTC.CTRLA` resets the prescaler and stretches the current PIT period, and clearing RTCEN stops the PIT (and clearing PITEN the RTC). So `hw::init` leaves `RTC.CTRLA` at its reset value and nothing writes it; if the clock check below wants RTCEN, set it once, before PITEN. Changing the PIT period means waiting for `RTC.PITSTATUS.CTRLBUSY`. `hw::set_output` already only runs when the output changes (`torch::Changes`), so the loop no longer rewrites the TCA0 compare buffers every tick or resets `TCA0_CNT` every tick while off. The simulator now takes interrupts and sleeps, and refuses an interrupt enabled with no handler, a `sleep` that nothing enabled could wake, and a busy-wait on the PIT flag. The watchdog's feeding doesn't change: the loop still wakes every tick, on or off, and feeds it every third, and the simulator counts WDT clocks asleep as well as awake. Still to check on a real light: the current draw on and off against the old busy-wait, and that clicks and holds still feel the same, which they should if the tick's still 64 Hz.
- [x] Battery voltage, with the ADC measuring the internal 1.5 V reference against VCC, four conversions accumulated, then the 0614 calibration (slope 1010/1024, +0.30 V) through `battery::centivolts`. The ADC alternates with the temperature sensor every 8 ticks (`src/sensors.rs`), throwing away the first conversion after each switch, and `src/hw.rs` has the setup ([hardware.md](hardware.md#the-driver) lists it). It runs on the simulated chip, which checks the setup and feeds scripted readings. Still to check on a real light: that the firmware's reading matches a multimeter at a few charge levels and under load. Stock Anduril on this light reads within 0.1 V at 3.57 to 4.08 V with the same method, which is encouraging, not proof.
- [x] Low-voltage protection, stepping down below 3.10 V and turning off below 2.99 V. The Wurkkos cell is unprotected and rated down to 2.50 V, and [hardware.md](hardware.md#the-driver) has the evidence. `battery::Protection` filters a sample every 16 ticks; after five seconds below 3.10 V the ceiling steps down 15 levels, after a second below 2.99 V the light turns off (or, on the FET, drops to the linear channel first), and it steps back up at 3.30 V. `src/limits.rs` fades the ceiling through a `Gradual` and turns the UI off on a flat cell. A voltage that can't be real (outside 2.00 to 4.60 V, a zero or saturated reading) never counts as safe: a second of them caps the light at level 75, and never turns it off. docs/ui.md has the rows. Still to check on a real light: the step-down and cut-off with a cell run down on a bench supply or for real, and how far the cell sags on the FET at turbo.
- [ ] Thermal regulation, using the internal temperature sensor (calibrated from `SIGROW.TEMPSENSE0` and `TEMPSENSE1`), a 45 °C limit (Anduril's default), and `thermal::Thermal`'s controller with prediction, a 2 °C hold window and a floor at the top of the linear channel. It's wired up: the ADC reads the temperature every 16 ticks while the light's on, `Thermal::reset` runs on turn-on, and the light runs at the lower of the UI's level and the ceiling. A broken sensor takes the ceiling to the floor. Not ticked because it can't do its job yet: the UI's one level (50) is under the floor, so it never visibly steps down, and its constants are tuned against a made-up model of the head. Still to do: the full UI with levels above 75, and a run up to temperature on a real light with a thermometer on the head (turbo until it steps down) to check the reading and retune. Stock Anduril read 20 °C against a 20.6 °C room on this light, with its own formula.
- [ ] A watchdog, so a hang can't leave the FET on. Anduril has no precedent here: it only uses the WDT to reboot, with an 8 ms timeout. The WDT runs off a 1.024 kHz clock from the same ultra-low-power oscillator as the PIT, and keeps counting in every sleep mode, so the off tick has to feed it too. Enable it from software through `CPU.CCP` (the IOREG key), waiting for `WDT.STATUS.SYNCBUSY` before each write to `WDT.CTRLA`. Leave `WDT.STATUS` LOCK alone, since only debug mode can clear it, and never use the `WDTCFG` fuse: a non-zero `WDTCFG` sets LOCK at boot (§19.3.3.3), so the fuse check below requires 0. Done so far: `hw::init` turns it on in window mode, `watchdog::Feeder` picks the passes of the main loop that feed it, and the simulator fails a firmware that leaves it off, feeds it in or on the edge of the closed window, or lets the open window run out. Not ticked until the on-chip proof and the reset-cause handling below are done. Still to check on a real light: that it never trips in normal use (a spurious reset shows as the light turning itself off).
  - Run it in window mode, as [AN2632](microchip/README.md) §3.2 recommends, so a jump into the wrong code fails whether it feeds the watchdog too late or too early, with the closed window at least half the period.
  - Size the window in ticks. The WDT and the PIT share an oscillator, so their drift cancels, and a 64 Hz tick is 16 WDT clocks. Feeding every tick lands on a window edge whatever the setting; 32 clocks closed and 32 open, fed every third tick (47 ms against a 31 to 62 ms open window), puts each feed mid-window. That's our arithmetic, not the app note's. Window mode only starts at the first `wdr` (DS §19.3.3.2), with only the 32-clock open window before it, so the first pass of the loop feeds it straight away, which also lines the windows up with the ticks. Done: `hw::init` sets `WINDOW` and `PERIOD` to `32CLK`, and the library's `watchdog::Feeder` counts the ticks. It also means the PIT can't slow down when off unless `WDT.CTRLA` is rewritten each time.
  - Feed from one place in the main loop, never from an interrupt handler (AN2747C §4). A second `wdr` while the first is still synchronising, 2 to 3 WDT clocks, is ignored (§19.3.6). Done: `src/main.rs` has the only `hw::feed_watchdog` call.
  - Still to do: prove it before trusting it, in AN2632 §6.1's four steps: a timeout resets the chip, a feed in time doesn't, an early feed in window mode does, then the real setup. §6.1 also checks the WDT period against TCA0 to within T/2 to 3T/2, which can share a pass with the clock check below.
  - Still to do: telling those deliberate resets apart from a real hang needs `RSTCTRL.RSTFR` (sticky, cleared by writing 1; a UPDI flash sets UPDIRF, not PORF, so that's a reset that reruns the test too) and a marker byte that survives reset. `src/rt.rs` zeroes `.bss`, so that means a `.noinit` section in `link.x`.
- [ ] Check the main clock against the RTC, using AN2632 §8's method. The RTC runs off the separate 32 kHz oscillator, so count TCA0 overflows between RTC ticks and fail if the count is outside a tolerance. That catches a dead 32 kHz oscillator, a broken timer or a main clock that's badly wrong, any of which throws off PWM, the tick and every filter timed by it. On a failure, turn the outputs off and stay off. The tolerance has to be wide: the 32 kHz oscillator is ±3% at 25 °C, ±10% from 0 to 70 °C and ±30% over the full range (DS table 36-13, characterised, not production tested), against ±2 to 5% for the 20 MHz one. So it can't tell 16 MHz from 20 MHz; that's the fuse check's job. The same spread applies to the tick: "64 Hz" could be anywhere from about 45 to 83 Hz, and the click timings, the five seconds in low-voltage protection and the thermal predictor all scale with it. If that matters, the measured ratio can correct the tick to within a few percent.
- [x] Check flash against a CRC at power-on (AN2632 §3.6 and §9.1), using the hardware `CRCSCAN`. Setting `CRCSCAN.CTRLA.ENABLE` starts it from software, with no fuse involved (the start-up scan is `SYSCFG0.CRCSRC`, a fuse, so it's off the table). `hw::flash_ok` runs it first thing in `main`, and a mismatch quietly refuses the FET, like a bad fuse (docs/ui.md). The simulator runs the CRC over its flash, which is the image `cargo xtask hex` writes, so a wrong sum in `xtask/src/crc.rs` fails it, and `flash:corrupt` in a script breaks a byte. Still to check on a real light: that a fresh flash goes above level 75 once the full UI's back. If it won't, suspect the CRC convention before the flash.
  - With `BOOTEND` and `APPEND` at 0, only the whole-flash scan works, and it expects the checksum in the last two bytes of flash, high byte first (DS §27.3.2.1, table 27-1). So `cargo xtask hex` and `flash` pad the image with 0xFF to 16 KB and put the CRC at 0x3FFE. The programmer skips blank pages after the chip erase, so that costs one extra page write, but `verify` now reads back all 16 KB.
  - The sum is CRC-16 CCITT, polynomial 0x1021, seed 0xFFFF, fed most significant bit first (DS §27.2 and figure 27-1): CRC-16/CCITT-FALSE, no reflection and no final XOR, so `crc16("123456789")` is 0x29B1. Over all of flash, the checksum included, that comes to 0, which is how the scan passes. AN2632 §9.1's seed of 0x0000 is for its software version, though it also says the two agree. Check `xtask`'s sum against a real chip before trusting it.
  - It isn't free: the only mode, priority, stalls the CPU, about 2.5 ms for 16 KB at 10 MHz, and the scan halts in sleep. It runs before `hw::init`, at the reset clock of 3.3 MHz, so about 7 ms.
  - Polled, not the NMI. `STATUS.OK` reads 1 from reset and the scan starts three cycles after ENABLE (§27.3.1), so `hw::flash_ok` waits four `nop`s (one spare, since the datasheet doesn't say when the three cycles start) before polling `BUSY`, or it could read the reset value as a pass. The simulator returns the stale STATUS for three instructions after the write. AN2521A §5 and §6 confirm the convention: its post-build step is `srec_cat -CRC16_Big_Endian -broken` (the 0xFFFF-seeded, non-augmented CCITT) and a signed section scans to 0x0000.
  - A half-written flash from an interrupted `cargo xtask flash` is the realistic fault here, not a bit flip.
- [x] Read the fuses back at power-on and refuse the FET if they're not what the firmware expects (AN2632 §11). Reading is safe; this never writes them. `selftest::Fuses::ok` has the rules, `hw::fuses` reads them before `hw::init`, and a failure quietly caps the light at level 75 for as long as the cell's in (docs/ui.md has the rows). The simulator serves the fuse bytes from the world (`fuse:OSCCFG=0x01` in a script) and refuses any write to them. Still to check on a real light: that its `backup/fuses.hex` passes, which `cargo xtask backup` gives you before the first flash.
  - Check `WDTCFG` is 0 (otherwise the watchdog's locked), `OSCCFG.FREQSEL` is 20 MHz with `OSCLOCK` clear (errata 2.2.1: OSCLOCK stops the oscillator calibration loading, and all the timing assumes a calibrated 20 MHz), `SYSCFG0.RSTPINCFG` is UPDI, and `BOOTEND` and `APPEND` are 0, since the vector table is linked at 0.
  - Compare fields, not whole bytes. The datasheet, the errata and the ATDF disagree on the factory `OSCCFG` and `SYSCFG0` bytes, and the ATDF's initvals aren't factory values at all (errata §3.1.1).
- [ ] Find out whether the BOD's on. Read the BOD settings from `BOD.CTRLA` and `CTRLB`, which mirror `BODCFG`, and check `RSTCTRL.RSTFR.BORF` for a brown-out reset. The errata gives a factory `BODCFG` of 0x00, which is BOD off, and the voltage level monitor only runs when the BOD does (§17.3.1). If a `cargo xtask backup` of a stock light confirms that, the firmware can rely on neither and leans on low-voltage protection. Nobody's read one off a TS21 yet, so the fuse check above leaves `BODCFG` alone.
  - If the BOD turns out to be on, set `BOD.CTRLA.SLEEP` to disabled or sampled under `CPU.CCP`. Continuous BOD is about 19 µA, against 1 or 2 µA for the sleeping chip with the PIT and the WDT running (DS tables 36-5 and 36-7, AN2515C §8.2).
  - If the BOD is on, check its level against the cut-off. Level 2 trips at 2.4 to 2.9 V of VCC, and VCC is probably about 0.3 V under the cell, so in the worst case it resets the chip with the cell around 3.2 V, above the 3.10 V step-down.
- [x] Decide what happens near 2.7 V of VCC. The datasheet only specifies 10 MHz from 2.7 V up (DS40002204A, table 36-3), and AN2747C §3 lists what goes wrong below a chip's limits: wrong execution and corrupted registers or flash. The firmware now runs at 5 MHz all the time, in spec down to 1.8 V, so it doesn't matter where VCC sits ([hardware.md](hardware.md#the-driver) has the reasoning). A higher cut-off or a clock change below some voltage would both have missed sag on the FET, which comes quicker than the filter sees it.
- [ ] Measure the drop from the cell to VCC on a real light, with a meter on the V and G pads against the cell: off, on low, at the top of the linear channel and on turbo. A bench supply stepped from 4.2 V to 2.5 V would be better still. The clock no longer depends on it, but it's what checks the calibration near 3 V (see the open questions in [hardware.md](hardware.md#open-questions)).
- [ ] Check 5 MHz on a real light: that level 150 and level 75 look as bright as they did at 10 MHz, which is the single-slope compare of 255 holding the pins high, that level 1 does too, since a compare of 1 is where an off-by-one in the duty would show, that there's no new whine, and that the off current hasn't moved.

## 3. It's nice to use

- [ ] Battery check on 3C
- [ ] Remember the level in RAM, in an ordinary static. The torch sleeps when it's off rather than losing power, and SRAM is kept through sleep (DS §11.2), so the firmware never needs to write EEPROM. It waits for the full UI, since `ui::LEVEL` is a constant today. Here's what that costs:
  - A cell swap loses the level, since RAM goes with the power.
  - Any reset loses it, not only a power-on. Every reset starts at `__reset`, and `src/rt.rs` never reads `RSTCTRL.RSTFR`, so the RAM test overwrites all of SRAM each time, and then `.data` and `.bss` are set up again. That covers a watchdog reset, a UPDI flash, a brown-out if the BOD's on, and a software reset if anything ever does one (nothing does yet). The torch comes back at its starting level. A `.noinit` section wouldn't survive either, and that includes the marker byte in the watchdog item above. Keeping anything through a reset would mean skipping the RAM test unless `PORF` is set.
  - USB charging should keep it, since the cell stays in. Likely, not confirmed: [hardware.md](hardware.md) has charging on a separate IP5310 and says nothing about what it does to the rail, and a charger that pulls VCC down far enough to reset the chip would lose the level too. Still to check on a real light: set a level, charge it, and see if the level's still there.
- [ ] Dynamic PWM (variable TCA0 TOP) for a smoother, dimmer bottom end. Set `TCA0.CTRLESET.LUPD` while writing `PERBUF` and both `CMPnBUF`, then clear it, so they all land on the same update (DS §20.3.3.3). Otherwise one cycle can run a new compare against the old TOP, and a compare above TOP holds the output high: the FET full on for a cycle. A longer period also changes the ADC noise picture (AN2551C §2.2). At TOP 255 a four-sample burst spans about four PWM periods and walks through the phase, but a period around 800 µs is longer than the burst, so the reading would depend on where in the cycle it starts. Either start conversions from a TCA0 event or accept the spread at low levels, where the current's small anyway.
- [x] Gradual level changes, so the step-downs in stage 2 aren't noticeable. `gradual::Gradual` does the fading, a level at a time with separate rates down and up, and both the thermal and the battery ceilings run through it on the torch (`src/limits.rs`).
- [ ] A version check that blinks out the build

## Maybe

- Configurable floor, ceiling and thermal limit
- [x] A UI simulator that runs `src/ui.rs` in a terminal: `cargo xtask simulate`
- Support for the TS10 and other lights that share this driver layout
- ADC noise tricks from AN2551C, sample delay (`SAMPDLY`) and its automatic variation (`ASDV`), probably aren't worth it. Errata 2.4.1 says they only work with `SAMPLEN` at 0, and the temperature sensor needs a 32 µs sample, which `SAMPLEN` 20 gives at 625 kHz with no margin. If the ADC clock ever changes, recompute it, and avoid `SAMPLEN` 19, which makes a conversion exactly one PWM period long and locks the reading to one phase
- [x] A RAM test at power-on, the March test AN2632 §9.2 describes, plus a stuck-bit check on the CPU registers (§3.1). Class B wants both, but they guard against silicon faults, which are rarer than the software and flashing faults the stage 2 checks cover, so this was done to learn how they work. `src/rt.rs` runs both before memory's set up: 0x55, 0xAA, 0x33, 0xCC, 0x0F and 0xF0 through r0 to r31, SREG without the I bit and SP's bits up to 0x3FFF, then March X over all of SRAM once each with the backgrounds 0x00, 0x55, 0x33 and 0x0F. A failure stops there with the FET and linear pins held low (AN2632 §5 says no functions should run). The simulator sweeps every stuck bit of r0 to r31, SREG and SP, every short between two of their bits, and a spread of RAM faults (`ram:` and `reg:` in a script), checks the right test caught each one, and lets something through if any check is taken out. That's how it found that a Z flag stuck at 1 made every compare pass, so the test now starts with one that mustn't, and that a T flag shorted to Z held every compare equal the same way, so the later SREG patterns clear SREG before comparing. Still open: RAM coupling faults aren't modelled, so nothing proves the ⇓ pass finds them. it only runs at power-on, so a fault that turns up with the cell in waits for the next cell swap; Class B also wants a periodic test, which means testing SRAM in sections around the live stack (AN2632 §9.2). And it's about 85 ms by my count of cycles, at 3.3 MHz before `hw::init`, not measured on a real chip
- [x] The write-page NVM command (0x01) for flash in place of page erase-write (0x03), since `program` chip-erases first. That's one erase per page per flash instead of two, and saves up to half a second (the datasheet's table 36-38 gives 2 ms for a page write against 4 ms for erase-write). `Programmer::erase_and_write_flash` does the chip erase and the page writes in one call, so nothing can page-write over flash that isn't blank, and `verify` catches an erase that didn't take. EEPROM keeps erase-write, since EESAVE can keep it through a chip erase.
