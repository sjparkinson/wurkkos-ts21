# Roadmap

Roughly in order. Each step should leave a torch that's no worse than the step before. Tick things off here in the commit that does them.

## 1. It lights up

- [x] Toolchain with nightly `avr-none`, `rust-lld`, own linker script and vector table, no crates
- [x] Pin map and registers for the TS21 (model 0614) driver
- [x] Switch sampling at 64 Hz and a click/hold decoder
- [x] Two-channel ramp (linear then FET), 150 levels
- [x] Click on, click off, at one level on the linear channel
- [x] A built-in UPDI programmer in `xtask` (ping, backup, flash, restore), tested against a fake chip
- [ ] Ping, back up and flash a real TS21, which is also the first real test of the programmer
- [ ] Confirm the batched UPDI frames work on a real chip. `write_page` now sends the RSD toggle, REPEAT, the page data and the RSD toggle back in one frame, and `read` sends REPEAT and LD together. The fake chip is happy with both; if a real flash fails partway through a page, split them back into separate sends first. Flash is committed with PAGEWRITE (0x01) and EEPROM with PAGEERASEWRITE (0x03), and only the fake chip has seen either, so if flash fails `verify` and EEPROM doesn't, suspect PAGEWRITE.
- [ ] See whether the `wait_nvm` after `NVM_PAGE_BUFFER_CLEAR` ever sees the controller busy. pymcuprog waits there, so keep it unless a real chip shows the first poll is always idle. It's one round trip per page.
- [x] Check PB5 is the button LED and decide what it does: amber, always on, lit by its pull-up
- [ ] See the amber button LED glow on a real TS21, which is the first check that PB5 is it
- [ ] Bring back the full UI from the `fancy-ui` branch, with ramping, moonlight, turbo and lockout

## 2. It's safe to leave a cell in

None of this is optional for a light with a direct-drive FET on a 21700.

- [x] Sleep when off, in power-down. Power-down draws the same as standby with everything stopped, and the PIT still runs in it (DS40002204A §23.8), so standby buys nothing here, and the one loop carries on every tick, on or off. That leaves the watchdog's feeding as it was (the WDT counts in every sleep mode, §19.3.4), and samples PA5 every tick, so PA5 needs no interrupt. PA5 is only partially asynchronous, so a pin-change wake would need a level that lasts until the clock restarts (table 16-3), and a press seen by the PIT tick has no such trouble. `Torch::resting` is true with the light off and no click being counted, and `hw::wait_for_tick` powers down on it. `Limits::rest` stops the ADC work, since it can't run in power-down (§30.3.5), so a press restarts the voltage readings, in time for the click, and a battery ceiling only climbs while the cell's being read. After five minutes of rest (`battery::FORGET_TICKS`) the filter forgets the cell, so the first reading stands alone. Any sooner and clicking off and on would reseed it from the unloaded voltage each time, keeping a nearly flat cell running. Anduril also slows the PIT when off, but that fights the watchdog window (see the watchdog item), and the off pass is only about 440 instructions. That's about 50 µs awake with the 10 µs wake-up (table 36-6), so around 10 µA on top of a sleeping chip's 1 or 2 µA. Likely, not measured. The button LED's pull-up dwarfs that at 50 to 64 µA, so the torch comes to about 600 mAh a year, before the rest of the driver. A separate rest loop that skips `Torch::tick` could save most of the 10 µA, but next to the LED that isn't worth a second place feeding the watchdog. A handler still mustn't touch TCA0's 16-bit registers, since they share one TEMP byte with the main loop and an interrupt mid-access corrupts it (§8.5.6), or it has to save and restore TEMP. The simulator lands both handlers on the instructions a run reaches, between a TCA0 low and high byte included, and refuses a handler that touches those registers there. It also lands the real tick on each of the instructions before `sleep`, which nothing but a long pass could do now the switch has no interrupt. Interrupts wait out the CCP window (§8.5.7), four instructions after a write to SPL or the next I/O write (§8.5.4), and the instruction after `sei` (DS40002198C), all from the documents and still to check on a real light. Before sleeping, `hw::prepare_sleep`:
  - Turns ADC0 off, and clears `VREF.CTRLB.ADC0REFEN`, which forces the reference on. The datasheet gives no current for either left on in power-down, and Anduril turns the ADC off too. `hw::adc_start` turns both on again when `sensors::Schedule` next sets the ADC up, and the conversion it throws away gives the reference a tick to start.
  - Checks both TCA0 compare registers are at 0, not only the BUF registers, and that no buffer's waiting for an UPDATE. `hw::set_output` forces the off row live as the output goes off, rather than waiting for a BOTTOM a stopped TCA0 never reaches, so the pass that turns the light off is the one that powers down. It clears CMPnEN then as well, leaving the pins to PORT, whose OUT is 0, so nothing here depends on what a waveform output does in sleep.
  - Leaves the unused pins as `hw::init` set them, pulled up with their input buffers off (AN2515C §9), all but PA0, which is UPDI.
- [ ] Measure the off current on a real light, against the 60 to 75 µA or so above, chip and button LED together. Whether the BOD's on matters here (see the BOD item), and so does whatever the rest of the driver draws. It's also the check that a `wdr` survives power-down: §19.3.6 has it syncing for 2 to 3 WDT clocks, the loop sleeps straight after feeding, and the datasheet doesn't say the sync finishes with the peripheral clock stopped. If it doesn't, the chip resets over and over while off, which looks like milliamps here and nothing else, since the light stays off and a press idles, so feeds land.
- [x] Sleep between ticks, in idle sleep, with the RTC PIT interrupt in place of the busy-wait. It did this off as well as on, until power-down (above) took over when off. Standby is out: TCA0 has no RUNSTDBY, so standby stops the PWM (§11.3.2.1). `hw::rtc_pit` clears the PIT's flag and sets a bit in `GPIOR0` (AN2515C §4.5 suggests GPIORs for shared flags, since `sbi` and `cbi` reach them in one instruction), and that's all. `hw::wait_for_tick` uses AN2515C §4.5's pattern so it can't sleep through a tick that's already happened: with interrupts off, check and clear the bit, and if it wasn't set, `sei` and `sleep` back to back, since the instruction after `sei` always runs before a pending interrupt. `hw::init` sets `RTC.PITINTCTRL.PI` before `PITEN`. Errata DS80000886C 2.6.1 and 2.6.2: any write to `RTC.CTRLA` resets the prescaler and stretches the current PIT period, and clearing RTCEN stops the PIT (and clearing PITEN the RTC). So `hw::init` leaves `RTC.CTRLA` at its reset value and nothing writes it; if the clock check below wants RTCEN, set it once, before PITEN. Changing the PIT period means waiting for `RTC.PITSTATUS.CTRLBUSY`. `hw::set_output` already only runs when the output changes (`torch::Changes`), so the loop no longer rewrites the TCA0 compare buffers every tick or resets `TCA0_CNT` every tick while off. The simulator now takes interrupts and sleeps, and refuses an interrupt enabled with no handler, a `sleep` that nothing enabled could wake, and a busy-wait on the PIT flag. The watchdog's feeding doesn't change: the loop still wakes every tick, on or off, and feeds it every third, and the simulator counts WDT clocks asleep as well as awake. Still to check on a real light: the current draw on and off against the old busy-wait, and that clicks and holds still feel the same, which they should if the tick's still 64 Hz.
- [x] Battery voltage, with the ADC measuring the internal 1.5 V reference against VCC, four conversions accumulated, then the 0614 calibration (slope 1010/1024, +0.30 V) through `battery::centivolts`. The ADC alternates with the temperature sensor every 8 ticks (`src/sensors.rs`), throwing away the first conversion after each switch, and `src/hw.rs` has the setup ([hardware.md](hardware.md#the-driver) lists it). It runs on the simulated chip, which checks the setup and feeds scripted readings. Still to check on a real light: that the firmware's reading matches a multimeter at a few charge levels and under load. Stock Anduril on this light reads within 0.1 V at 3.57 to 4.08 V with the same method, which is encouraging, not proof.
- [x] Low-voltage protection, stepping down below 3.10 V and turning off below 2.99 V. The Wurkkos cell is unprotected and rated down to 2.50 V, and [hardware.md](hardware.md#the-driver) has the evidence. `battery::Protection` filters a sample every 16 ticks; after five seconds below 3.10 V the ceiling steps down 15 levels, after a second below 2.99 V the light turns off (or, on the FET, drops to the linear channel first), and it steps back up at 3.30 V. `src/limits.rs` fades the ceiling through a `Gradual` and turns the UI off on a flat cell. A voltage that can't be real (outside 2.00 to 4.60 V, a zero or saturated reading) never counts as safe: a second of them caps the light at level 75, and never turns it off. docs/ui.md has the rows. Still to check on a real light: the step-down and cut-off with a cell run down on a bench supply or for real, and how far the cell sags on the FET at turbo.
- [ ] Thermal regulation, using the internal temperature sensor (calibrated from `SIGROW.TEMPSENSE0` and `TEMPSENSE1`), a 45 °C limit (Anduril's default), and `thermal::Thermal`'s controller with prediction, a 2 °C hold window and a floor at the top of the linear channel. It's wired up: the ADC reads the temperature every 16 ticks while the light's on, `Thermal::reset` runs on turn-on, and the light runs at the lower of the UI's level and the ceiling. A broken sensor takes the ceiling to the floor. Not ticked because it can't do its job yet: the UI's one level (50) is under the floor, so it never visibly steps down, and its constants are tuned against a made-up model of the head. Still to do: the full UI with levels above 75, and a run up to temperature on a real light with a thermometer on the head (turbo until it steps down) to check the reading and retune. Stock Anduril read 20 °C against a 20.6 °C room on this light, with its own formula.
- [ ] A watchdog, so a hang can't leave the FET on. Anduril has no precedent here: it only uses the WDT to reboot, with an 8 ms timeout. The WDT runs off a 1.024 kHz clock from the same ultra-low-power oscillator as the PIT, and keeps counting in every sleep mode, so the off tick has to feed it too. Enable it from software through `CPU.CCP` (the IOREG key), waiting for `WDT.STATUS.SYNCBUSY` before each write to `WDT.CTRLA`. Leave `WDT.STATUS` LOCK alone, since only debug mode can clear it, and never use the `WDTCFG` fuse: a non-zero `WDTCFG` sets LOCK at boot (§19.3.3.3), so the fuse check below requires 0. Done so far: `hw::init` turns it on in window mode, `watchdog::Feeder` picks the passes of the main loop that feed it, the simulator fails a firmware that leaves it off, feeds it in or on the edge of the closed window, or lets the open window run out, and the proof and reset-cause handling below are in. Not ticked until the proof has passed on a real chip. Still to check on a real light: that it never trips in normal use (a spurious reset shows as the light turning itself off, then staying under level 75 until the cell comes out).
  - Run it in window mode, as [AN2632](microchip/README.md) §3.2 recommends, so a jump into the wrong code fails whether it feeds the watchdog too late or too early, with the closed window at least half the period.
  - Size the window in ticks. The WDT and the PIT share an oscillator, so their drift cancels, and a 64 Hz tick is 16 WDT clocks. Feeding every tick lands on a window edge whatever the setting; 32 clocks closed and 32 open, fed every third tick (47 ms against a 31 to 62 ms open window), puts each feed mid-window. That's our arithmetic, not the app note's. Window mode only starts at the first `wdr` (DS §19.3.3.2), with only the 32-clock open window before it, so the first pass of the loop feeds it straight away, which also lines the windows up with the ticks. Done: `hw::init` sets `WINDOW` and `PERIOD` to `32CLK`, and the library's `watchdog::Feeder` counts the ticks. It also means the PIT can't slow down when off unless `WDT.CTRLA` is rewritten each time.
  - Feed from one place in the main loop, never from an interrupt handler (AN2747C §4). A second `wdr` while the first is still synchronising, 2 to 3 WDT clocks, is ignored (§19.3.6). Done: `src/main.rs` has the only `hw::feed_watchdog` calls, one in the loop and one in the proof, which runs instead of the loop.
  - Prove it before trusting it, in AN2632 §6's four steps (they're on page 17, and §6.1 is how to test the routine): a timeout resets the chip, a feed in time doesn't, an early feed in window mode does, then the real setup. Done on the simulator: `watchdog::Proof` walks them on a power-on or UPDI reset, each step a boot with one write of `WDT.CTRLA`, all timed in ticks so the oscillator's spread can't fail a good chip, and three deliberate resets in all. A bite the marker wasn't expecting fails the proof, so does a bite that doesn't come, and a failure refuses the FET, like a bad fuse. It's different in one way: the failed chip runs on an 8 s timeout with no window, since a watchdog that bites early would otherwise reset it for good, feeds on time and all. One that ignores its feeds still bites at 8 s, so that light turns itself off every 8 s. The simulator runs every case on the real firmware: a chip that's fine, a UPDI reset, a watchdog that never bites, bites early, ignores a feed, stops once fed, lets an early feed through or never opens its window, and SRAM that doesn't survive the reset, each found at the step that should find it (`wdt:` in a script). It counts the WDT in whole ticks, so it can't show how the phase of the first tick plays out. It lets something through if any check in the proof is taken out. What it can't see, as with flash and fuses, is the firmware ignoring the verdict: the cap only shows above level 75, and the UI stops at 50, so nothing catches `src/main.rs` dropping `proof.refused()` until the full UI's back. §6 also checks the WDT period against TCA0 to within T/2 to 3T/2, which is for the clock check below, and a feed in the open window, which the loop's second feed does anyway: a window that never opens shows up as a hang. Step 2 only fails a watchdog that bites in under half its period, so one between 50% and 75% of it passes the proof, then resets the loop over and over as a hang, which stays dark rather than capped. Still to check on a real light: all of it, starting with SRAM surviving a watchdog reset. AN2632 §6 says so, the datasheet doesn't (table 12-1 even marks "other volatile logic" as reset, without saying what that covers), and if it doesn't, the proof fails on a good chip and the light never goes over level 75. Then that a `wdr` survives power-down, which the proof doesn't cover, since it stays in idle. The loop feeds and sleeps at once, mid-sync (see the off-current item above), and if that feed gets lost, the bite that follows now counts as a hang: a light left off would quietly refuse the FET until the cell comes out. So leave one resting for a while, then check it still goes above level 75.
  - What a reset means. Done: `hw::take_reset_flags` reads `RSTCTRL.RSTFR` and clears it on every boot (sticky, cleared by writing 1; a UPDI flash sets UPDIRF, not PORF, so that's a reset that reruns the proof too), and a marker in `.noinit` (`link.x`, two bytes, the second the complement of the first) carries the proof's step across a reset. `Proof::after_reset` has the rules. A bite after the proof has passed is a hang: the light comes back off and refuses the FET for as long as the cell's in. So is no flag at all, which means something jumped to the reset vector. `src/rt.rs` zeroes `.bss`, and its RAM test overwrites all of SRAM, `.noinit` with it. So the test runs on a power-on or UPDI reset, where the marker doesn't matter, and after a hang, with the marker held in r2 and r3 across it. That's what makes a failed periodic section end for good on a fault that's still there. The proof's own resets skip it, saving 85 ms on each, and so do brown-out and software resets, so a brown-out gets no RAM test.
  - The time it adds, by the sums, since none of this has been timed on a chip. Step 1 is about 11 WDT clocks, step 2 54 to 70 and step 3 22 to 38, so 90 to 120 ms at a nominal 1.024 kHz, and 30% more at the slow end of table 36-13. Each of the three resets also costs the fuses' start-up time: `SYSCFG1.SUT` is 64 ms from the factory (errata §3.1.1), though nothing's read it off this light. §12.3.2.2 adds it after any reset, while §6.10.4.6 calls it the time from power-on, so it's likely 192 ms, and might be nothing. Only a measurement settles that. That's about 0.3 s before the torch responds, on top of the 150 ms or so a power-on already took. Only a fuse could shorten the 192 ms, so that stays. A press isn't lost: the proof samples the switch as each boot starts and on every tick, and the marker carries it through the resets, so the loop counts a press on its first tick. That can't see the 64 ms of a reset, so a press that starts and ends inside one is gone, and a quick click could. Merging steps 1 and 2 would save a reset, 75 ms or so, and still show everything: a feed that holds off a timeout and then the timeout. It'd stop matching AN2632's steps one for one, so it isn't done.
  - The outputs through all that. TCA0 runs from `hw::init` with both compares at 0 and nothing calls `hw::set_output` during the proof, so the pins are held low, as they are with the light off, and the simulator checks that on every instruction. What firmware can't do is hold them through a reset: every pin goes to an input, floating, for the start-up time above, until `src/rt.rs`'s first two instructions. The gates were driven low just before, so they should stay low, but nobody knows if there's a pull-down on them. Still to check on a real light, with a scope on the gates: that the FET stays off through all three resets. The same float comes after a real hang, when a gate can start high: the FET could stay on for those 64 ms.
- [x] Check the main clock against the RTC, using AN2632 §8's method. The RTC runs off the separate 32 kHz oscillator, so count TCA0 overflows between RTC ticks and fail if the count is outside a tolerance. That catches a dead 32 kHz oscillator, a broken timer or a main clock that's badly wrong, any of which throws off PWM, the tick and every filter timed by it. On a failure, turn the outputs off and stay off. The tolerance has to be wide: the 32 kHz oscillator is ±3% at 25 °C, ±10% from 0 to 70 °C and ±30% over the full range (DS table 36-13, characterised, not production tested), against ±2 to 5% for the 20 MHz one. So it can't tell 16 MHz from 20 MHz; that's the fuse check's job. The same spread applies to the tick: "64 Hz" could be anywhere from about 45 to 83 Hz, and the click timings, the five seconds in low-voltage protection and the thermal predictor all scale with it. If that matters, the measured ratio can correct the tick to within a few percent. `hw::count_tick` polls the overflows instead of AN2632's interrupt, which would fire at 19.6 kHz, and `selftest::ClockCheck` passes 39,525 to 130,560 clocks against a nominal 78,125, less one PWM cycle at the bottom, and has the sums. `hw::count_tick` adds the length of each cycle that ends, so it's addition only, in a `u32`, and it reads that length from `TCA0.PER`, holding each reading back a cycle, since a period that's just changed only lands at BOTTOM. It uses the PIT's flag as the tick, so `RTC.CTRLA` stays untouched. It counts once at power-on, after the first tick since the first PIT period can be anything up to a full one (§23.5.2.2), and then once a second while the light's on, a counted wait in place of the idle sleep. TCA0 stops in power-down, so it doesn't count at rest, which is fine, since a torch that's off isn't timing anything.
  - A dead 32 kHz oscillator takes the PIT and the WDT with it, so the loop would never wake, and with the light on that's the light left on with no protection and no watchdog. So TCB0 is a deadline: `wait_for_tick` restarts it on each tick, and 26.2 ms later it wakes the CPU from idle, against the 22.3 ms the slowest good tick takes. `hw::init` gives up on the oscillator's sync flags after a bounded wait too, for one that's dead from power-on. A torch in power-down when it dies stays there, which is off: a press only wakes it as far as `wait_for_tick`'s loop, which goes back to sleep.
  - The failure isn't a separate halt. `Torch` stays off from then on, `hw::set_output` zeroes both compares directly when the output goes off, since a stopped TCA0 never reaches BOTTOM, so the next sleep is power-down, and the loop carries on feeding the watchdog if it's still got ticks, so a bad clock doesn't reset and start again. Taking the cell out runs it all again.
  - The proof runs first, then the first count, so a clock that's only slow still gets its watchdog proved, and nothing's lit for either. Every wait in the proof is for a tick, and a dead 32 kHz oscillator stops the WDT too, so no bite would ever end it. So `hw::init` saying the oscillator's dead, or `wait_for_tick` giving up on a tick, ends the proof through `Proof::no_tick`: the marker says it failed, a software reset follows, and that boot's `hw::init` finds the same dead oscillator and fails the clock check. `dead_oscillator` in `xtask/src/sim.rs` kills it on each boot of the proof, and the docs/ui.md row has it dead from power-on.
  - The floor has to cover the pass before the count, which goes uncounted, so it depends on how long a pass is. The periodic RAM test about doubled that, to about 3,300 instructions, so the floor went from 176 of the shortest cycles to 154, and `selftest::PASS_INSTRUCTIONS` is now what the sums allow, which `cargo xtask hex` holds the firmware to.
  - It shares its count with AN2632 §6's WDT period check, in that a tick is always 16 WDT clocks, so this bounds the WDT's clock at 0.50 to 1.67 of T. That's T/2 at the bottom. At the top it's wider than 3T/2, which is 460 overflows, right on the worst good chip. It says nothing about the WDT's own counter, which needs a real timeout timed through a reset, so that stays with the watchdog item.
  - Still to check on a real light: that a good chip counts near 306 at room temperature and doesn't trip when cold or hot, that the sync polls in `hw::init` outlast a real WDT and PIT sync (the datasheet gives no time, and the simulator clears those flags by reads, so it can't tell), that a dead 32 kHz oscillator can't stop the chip before it reaches `main` (the datasheet says the RTC is used during start-up, and doesn't say how), and that TCB0 wakes idle when nothing else does. The count assumes a TCA0 period of 255, so dynamic PWM has to count at a known PER or scale by it.
- [x] Check flash against a CRC at power-on (AN2632 §3.6 and §9.1), using the hardware `CRCSCAN`. Setting `CRCSCAN.CTRLA.ENABLE` starts it from software, with no fuse involved (the start-up scan is `SYSCFG0.CRCSRC`, a fuse, so it's off the table). `hw::flash_ok` runs it first thing in `main`, and a mismatch quietly refuses the FET, like a bad fuse (docs/ui.md). The simulator runs the CRC over its flash, which is the image `cargo xtask hex` writes, so a wrong sum in `xtask/src/crc.rs` fails it, and `flash:corrupt` in a script breaks a byte. Still to check on a real light: that a fresh flash goes above level 75 once the full UI's back. If it won't, suspect the CRC convention before the flash.
  - With `BOOTEND` and `APPEND` at 0, only the whole-flash scan works, and it expects the checksum in the last two bytes of flash, high byte first (DS §27.3.2.1, table 27-1). So `cargo xtask hex` and `flash` pad the image with 0xFF to 16 KB and put the CRC at 0x3FFE. The programmer skips blank pages after the chip erase, so that costs one extra page write, but `verify` now reads back all 16 KB.
  - The sum is CRC-16 CCITT, polynomial 0x1021, seed 0xFFFF, fed most significant bit first (DS §27.2 and figure 27-1): CRC-16/CCITT-FALSE, no reflection and no final XOR, so `crc16("123456789")` is 0x29B1. Over all of flash, the checksum included, that comes to 0, which is how the scan passes. AN2632 §9.1's seed of 0x0000 is for its software version, though it also says the two agree. Check `xtask`'s sum against a real chip before trusting it.
  - It isn't free: the only mode, priority, stalls the CPU, about 2.5 ms for 16 KB at 10 MHz, and the scan halts in sleep. It runs before `hw::init`, at the reset clock of 3.3 MHz, so about 7 ms.
  - Polled, not the NMI. `STATUS.OK` reads 1 from reset and the scan starts three cycles after ENABLE (§27.3.1), so `hw::flash_ok` waits four `nop`s (one spare, since the datasheet doesn't say when the three cycles start) before polling `BUSY`, or it could read the reset value as a pass. The simulator returns the stale STATUS for three instructions after the write. AN2521A §5 and §6 confirm the convention: its post-build step is `srec_cat -CRC16_Big_Endian -broken` (the 0xFFFF-seeded, non-augmented CCITT) and a signed section scans to 0x0000.
  - A half-written flash from an interrupted `cargo xtask flash` is the realistic fault here, not a bit flip.
- [x] Read the fuses back at power-on and refuse the FET if they're not what the firmware expects (AN2632 §11). Reading is safe; this never writes them. `selftest::Fuses::ok` has the rules, `hw::fuses` reads them before `hw::init`, and a failure quietly caps the light at level 75 for as long as the cell's in (docs/ui.md has the rows). The simulator serves the fuse bytes from the world (`fuse:OSCCFG=0x01` in a script) and refuses any write to them. Still to check on a real light: that its `backup/fuses.hex` passes, which `cargo xtask backup` gives you before the first flash.
  - Check `WDTCFG` is 0 (otherwise the watchdog's locked), `OSCCFG.FREQSEL` is 20 MHz with `OSCLOCK` clear (errata 2.2.1: OSCLOCK stops the oscillator calibration loading, and all the timing assumes a calibrated 20 MHz), `SYSCFG0.RSTPINCFG` is UPDI, and `BOOTEND` and `APPEND` are 0, since the vector table is linked at 0.
  - Compare fields, not whole bytes. The datasheet, the errata and the ATDF disagree on the factory `OSCCFG` and `SYSCFG0` bytes, and the ATDF's initvals aren't factory values at all (errata §3.1.1).
- [ ] Find out whether the BOD's on. Read the BOD settings from `BOD.CTRLA` and `CTRLB`, which mirror `BODCFG`, and check `RSTCTRL.RSTFR.BORF` for a brown-out reset. The errata gives a factory `BODCFG` of 0x00, which is BOD off, and the voltage level monitor only runs when the BOD does (§17.3.1). If a `cargo xtask backup` of a stock light confirms that, the firmware can rely on neither and leans on low-voltage protection. Nobody's read one off a TS21 yet, so the fuse check above leaves `BODCFG` alone.
  - If the BOD turns out to be on, set `BOD.CTRLA.SLEEP` to disabled or sampled under `CPU.CCP`. Continuous BOD is about 19 µA, against 1 or 2 µA for the sleeping chip with the PIT and the WDT running (DS tables 36-5 and 36-7, AN2515C §8.2).
  - If the BOD is on, check its level against the cut-off. Level 2 trips at 2.4 to 2.9 V of VCC, and VCC is probably about 0.3 V under the cell, so in the worst case it resets the chip with the cell around 3.2 V, above the 3.10 V step-down.
- [x] Decide what happens near 2.7 V of VCC. The datasheet only specifies 10 MHz from 2.7 V up (DS40002204A, table 36-3), and AN2747C §3 lists what goes wrong below a chip's limits: wrong execution and corrupted registers or flash. The firmware now runs at 5 MHz all the time, in spec down to 1.8 V, so it doesn't matter where VCC sits ([hardware.md](hardware.md#the-driver) has the reasoning). A higher cut-off or a clock change below some voltage would both have missed sag on the FET, which comes quicker than the filter sees it.
- [ ] Measure the drop from the cell to VCC on a real light, with a meter on the V and G pads against the cell: off, on low, at the top of the linear channel and on turbo. A bench supply stepped from 4.2 V to 2.5 V would be better still. The clock no longer depends on it, but it's what checks the calibration near 3 V (see the open questions in [hardware.md](hardware.md#open-questions)).

## 3. It's nice to use

- [ ] Battery check on 3C
- [ ] Remember the level in RAM, in an ordinary static. The torch sleeps when it's off rather than losing power, and SRAM is kept through sleep (DS §11.2), so the firmware never needs to write EEPROM. It waits for the full UI, since `ui::LEVEL` is a constant today. Here's what that costs:
  - A cell swap loses the level, since RAM goes with the power.
  - Any reset loses it, not only a power-on. Every reset starts at `__reset`, and `.data` and `.bss` are set up again each time, so an ordinary static goes back to its starting value whichever reset it was. `src/rt.rs` reads `RSTCTRL.RSTFR` now, and the RAM test also overwrites all of SRAM after a power-on, a UPDI flash or a hang. A `.noinit` section would get through the resets that skip it (the watchdog proof's own, a brown-out, a software or an external reset), but not those three: the proof's marker only survives the march because `src/rt.rs` carries it in r2 and r3. And SRAM surviving a reset at all isn't confirmed (see the watchdog item).
  - USB charging should keep it, since the cell stays in. Likely, not confirmed: [hardware.md](hardware.md) has charging on a separate IP5310 and says nothing about what it does to the rail, and a charger that pulls VCC down far enough to reset the chip would lose the level too. Still to check on a real light: set a level, charge it, and see if the level's still there.
- [x] Dynamic PWM (variable TCA0 TOP) for a smoother, dimmer bottom end. `ramp::Output` now carries a `top` as well as the two compares, 16 bits each, and the linear channel's half of the table picks both from a cubic curve in a `const fn`: TOP 4095 (1.22 kHz) at level 1, falling to 255 (19.6 kHz), with the shortest pulse 4 clocks, `ramp::MIN_PULSE`. Level 1 is a nominal 4/4095, four times dimmer than before, and every level of the linear channel is now brighter than the last, where the first twelve used to be the same. Level 75 and up, and off, stay at TOP 255, and the 150 levels and the crossover at 75 haven't moved. Full on is a compare equal to `top`, one over PER, and off is a compare of 0, with tests for both. [hardware.md](hardware.md#the-driver) has the frequencies and why they're what they are. `hw::set_output` sets `TCA0.CTRLESET.LUPD` while it writes `PERBUF` and both `CMPnBUF`, then clears it, so they all land on the same update (DS §20.3.3.3, §20.5.6). Otherwise one cycle can run a new compare against the old TOP, and a compare above TOP holds the output high: the FET full on for a cycle. `hw::init` now writes `PER` directly with the timer stopped, since `PERBUF` wouldn't reach it until the first cycle at 0xFFFF had run out, 13 ms later. The simulator counts to the live PER and applies the buffers at BOTTOM unless LUPD's set. Anything that goes live has to be a whole row of `ramp::output`, and it checks an unlocked write as if a BOTTOM landed straight after it, since a real one only falls between two writes now and then. `sim::check` runs the firmware on a chip that drops LUPD and fails unless that's caught, so the check can't rot. The UI only reaches level 50, so `src/bin/pwm_probe.rs` runs the real `hw::set_output` through every level, down to level 1 from each, and `sim::pwm_probe` checks each lands whole. TCA0 stops in power-down in the simulator, since §20.3.6 only promises idle, so `hw::output_settled` also waits for the buffer valid flags to clear. Going off doesn't wait for BOTTOM: `hw::set_output` clears CMPnEN first, then writes the off row under LUPD and forces it live with an UPDATE command, which LUPD doesn't hold back (§20.3.3.5), so the whole row lands at once and BV clears on that pass. Then it writes both compares to 0 directly, for a stopped TCA0 that might ignore a command too. Whether one does is unknown: the simulator has a case for each, and the second stays in idle, off. CMPnEN only comes back with a level asked for, and the simulator's waveform outputs are latches that hold when the timer stops, so a light stopped mid-pulse has to go out that way. A BOTTOM under LUPD might clear BV without copying anything, so `hw::set_output` reads the flags back while it's locked and writes the row again, and `hw::keep_output` reissues a row lost after that. The simulator runs the examples, the random switching and the probe under both readings. Only 0 ever goes in directly with the timer running, so that can't put a compare over PER. The clock check adds up clocks, not overflows, since a cycle can now be 16 times the length, and a count can start with the old period still live, so `hw::count_tick` takes each cycle's length from `TCA0.PER`. `sim::pwm_probe` runs the real count at levels 1, 50 and 150 and across the jumps between them, at both ends of the clocks' spread. For the ADC I've accepted the spread rather than start conversions from a TCA0 event. TOP is only longer than a four-conversion burst (1056 clocks) on levels 1 to 11, where the pulse is 0.8 µs and the draw about 1 mA at most, and an event start brings EVSYS, a fixed phase and errata 2.4.2. At TOP 255 a burst doesn't really walk through the phase, as this item used to say: a conversion is 264 clocks, so each start moves on 9 clocks, 27 over a burst, about a tenth of a cycle. What varies the phase is the PIT, on its own oscillator, from one reading to the next. `SAMPLEN` 20 and the ADC clock are unchanged, so the temperature sensor's 32 µs still has no margin, and errata 2.4.1 still rules out `SAMPDLY` and `ASDV`. A conversion is exactly one cycle at TOP 264, so the table steps off it. Still to check on a real light: whether a BOTTOM under LUPD clears BV, and so how often `hw::set_output` has to write a row again and `hw::keep_output` has to reissue one (the datasheet's ambiguous, see hardware.md, and the simulator runs both readings), what level a waveform output holds on a stopped TCA0, how the bottom end looks, that level 1 lights and whether `MIN_PULSE` wants changing, that the steps around levels 19 to 30 look even, since the compare's small there and the regulator's pulse response is only known from forum posts, flicker in a moving beam at levels 1 to 11, coil whine or any other noise from the low levels, that a change of level shows no blip, and whether the board has an inductor. The FET half keeps its plateaus, with levels 76 to 87 all at a compare of 1.

A lost long-to-short row can under-count the clock by up to 4,094 clocks in the worst case, which is the `pwm_probe` case. Some paths have no test: `write_row`'s give-up `CTRLFCLR`, the "left half done" check, and unit tests for `tca_deaf`, `adverse_bottom`, `lock_writes`, `tick_landed` and `tcb.probe`.

Errata 2.4.1 says they only work with `SAMPLEN` at 0, and the temperature sensor needs a 32 µs sample, which `SAMPLEN` 20 gives at 625 kHz with no margin. If the ADC clock ever changes, recompute it. A conversion is (13 + `SAMPLEN`) × 8 clocks, 264 at `SAMPLEN` 20, and a TOP that matches it exactly locks the reading to one phase, so `ramp::dynamic` works it out from `regs` and steps off that TOP. That's no longer `SAMPLEN` 19 against a fixed period: 19 would be 256 clocks, one over TOP 255
- [x] A RAM test at startup, the March test AN2632 §9.2 describes, plus a stuck-bit check on the CPU registers (§3.1). Class B wants both, but they guard against silicon faults, which are rarer than the software and flashing faults the stage 2 checks cover, so this was done to learn how they work. `src/rt.rs` runs the register test on every reset and the RAM test on a power-on or UPDI reset and after a hang, both before memory's set up: 0x55, 0xAA, 0x33, 0xCC, 0x0F and 0xF0 through r0 to r31, SREG without the I bit and SP's bits up to 0x3FFF, then March X over all of SRAM once each with the backgrounds 0xAA, 0x55, 0x33 and 0x0F. A failure stops there with the FET and linear pins held low (AN2632 §5 says no functions should run). The simulator sweeps every stuck bit of r0 to r31, SREG and SP, every short between two of their bits, a spread of RAM faults, and every coupling fault between two neighbouring bytes, flipping or forcing, either way round (`ram:` and `reg:` in a script), checks the right test caught each one, and lets something through if any check is taken out. That's how it found that a Z flag stuck at 1 made every compare pass, so the test now starts with one that mustn't, and that a T flag shorted to Z held every compare equal the same way, so the later SREG patterns clear SREG before comparing. It also shows the ⇓ pass earning its keep: a bit 7 going high that flips a bit in a byte below it is found there and nowhere else, and gets to `main` with that check patched out. And it found that with 0x00 as the first background, couplings that force a bit 7 got through, since bit 7 was 0 in all four, which is why it's 0xAA, at no extra cost. There's a periodic test as well, as Class B wants: `__ram_section` in `src/rt.rs` runs the same march on 16 bytes a tick from the main loop, moving on 8 at a time so each section overlaps the last (AN2632 §3.5), which makes a sweep of SRAM just under 4 seconds of light. The section's copy goes in r2 to r17 with interrupts off, so there's no buffer to test and the live stack needs no special case. A pass is 1,656 instructions, about 0.46 ms of a 15.6 ms tick at 5 MHz by my count of cycles. It doesn't run while resting: a pass is seven times what the torch stays awake for when off, and there's no output to guard, so a fault that turns up then waits until the light's next on. A failure hands the pins back to PORT, which holds them low (most likely at once; the datasheet gives no delay, and dropping a pin mid-pulse is still to check on a real light), then stops without feeding the watchdog, which resets the chip. That's a hang, so startup tests all of SRAM again, holding the watchdog's marker in r2 and r3 across it: a fault that's still there stops in `__selftest_failed` for good, and one that's gone comes back off with the FET refused. The simulator checks a whole sweep puts everything back and leaves the caller's registers alone, that each of the march's three checks finds a coupling the others don't and lets it through if patched out, that faults turning up mid-run are found, the live stack included, and that a coupling across a section boundary needs the overlap. It carries the same chip through the reset after a failure, and checks both of those ends, and that with the test after a hang patched out a lasting fault reaches `main`. DS40002204A's table 12-1 says a watchdog reset resets "other volatile logic" without saying whether SRAM keeps its contents. The march writes all of it before reading, so that most likely doesn't matter to the march, and if the marker's lost the light fails safe, but that isn't confirmed. Still open: within one byte, a coupling that forces bit 0 from bit 7 or the reverse gets through, and so do 1 and 6, 2 and 5, and 3 and 4, since each pair is opposite in every background. The periodic test only sees a fault within one section, so an address or coupling fault between bytes further apart still waits for the next cell swap, and a brown-out reset gets no RAM test at all. The full test is still about 85 ms by my count of cycles, at 3.3 MHz before `hw::init`. Neither time's been measured, and none of this has run on a real light yet
- [x] The write-page NVM command (0x01) for flash in place of page erase-write (0x03), since `program` chip-erases first. That's one erase per page per flash instead of two, and saves up to half a second (the datasheet's table 36-38 gives 2 ms for a page write against 4 ms for erase-write). `Programmer::erase_and_write_flash` does the chip erase and the page writes in one call, so nothing can page-write over flash that isn't blank, and `verify` catches an erase that didn't take. EEPROM keeps erase-write, since EESAVE can keep it through a chip erase.
